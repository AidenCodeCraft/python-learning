## 1. 数据库是什么

| 概念 | 含义 |
|---|---|
| **DB（数据库）** | 按一定结构组织、存储数据的"仓库" |
| **DBMS（数据库管理系统）** | 管理数据库的软件，如 MySQL / PostgreSQL / Oracle |
| **表（table）** | 一类数据的集合，由**行**和**列**组成 |
| **行 / 记录（row / record）** | 一条具体数据（一个员工、一笔订单） |
| **列 / 字段（column / field）** | 数据的一个属性（姓名、工资） |

**为什么不用 Excel / 文本文件存数据？**

| 需求 | Excel / 文件 | 数据库 |
|---|---|---|
| 多人同时读写 | ❌ 容易互相覆盖 | ✅ 事务 + 锁 |
| 数据量大（百万级） | ❌ 卡死 | ✅ 索引 + 分页 |
| 保证数据正确（不能有重复 id） | ❌ 靠人 | ✅ 约束 |
| 出故障不丢数据 | ❌ | ✅ 日志 + 备份 |
| 复杂查询（多表关联统计） | ❌ | ✅ SQL |

## 2. 关系模型：数据库的"世界观"

**一张表 = 一个关系**。每行是一条记录，每列是一个属性，列有固定类型。

**三种"键"（面试爱考）**：

| 键 | 定义 | 例子 |
|---|---|---|
| **主键 Primary Key** | 唯一标识一行；**不能为 NULL**；一张表只能有一个 | `employees.id` |
| **候选键 Candidate Key** | 能唯一标识行的所有列组合（主键是其中选出来的一个） | 身份证号也是候选键 |
| **外键 Foreign Key** | 指向另一张表主键的列，用来保证"引用的数据一定存在" | `employees.dept_id → departments.id` |

```text
departments                     employees
+----+--------+                 +----+------+---------+--------+
| id | name   |                 | id | name | dept_id | salary |
+----+--------+                 +----+------+---------+--------+
| 1  | 研发部 |  ←──外键──────── | 1  | 张伟 |    1    | 25000  |
+----+--------+                 +----+------+---------+--------+
```

> **现实补充**：互联网公司（包括你们）很多表**不加物理外键**，只在应用层保证 —— 因为外键会影响性能、也不方便分库分表。但**概念必须懂**，设计时要能说出"这里有外键关系"。

## 3. SQL 的五大分类（面试常问）

| 分类 | 全称 | 包含语句 | 管什么 |
|---|---|---|---|
| **DDL** | Data **Definition** Language | `CREATE` / `ALTER` / `DROP` / `TRUNCATE` / `RENAME` | 表**结构** |
| **DML** | Data **Manipulation** Language | `INSERT` / `UPDATE` / `DELETE` | 表**数据** |
| **DQL** | Data **Query** Language | `SELECT` | **查询**（有时并入 DML） |
| **DCL** | Data **Control** Language | `GRANT` / `REVOKE` | **权限** |
| **TCL** | **Transaction** Control Language | `START TRANSACTION` / `COMMIT` / `ROLLBACK` / `SAVEPOINT` | **事务** |

> 记忆：**D 定义、M 改数据、Q 查、C 控权限、T 管事务。**

## 4. 数据类型怎么选（建表必用）

| 类型 | 用途 | 怎么选 |
|---|---|---|
| `TINYINT` | 布尔值 | `is_deleted TINYINT(1) DEFAULT 0`（MySQL 没有真 bool） |
| `INT` | 整数 | 最大约 21 亿 |
| `BIGINT` | 大整数 | **用户 id / 订单 id 用 BIGINT**（INT 会不够用） |
| `VARCHAR(n)` | 变长字符串 | 姓名 50、手机号 20、邮箱 100 |
| `CHAR(n)` | **定长**字符串 | 只适合长度固定：性别、国家代码（`CHAR(2)`） |
| `TEXT` | 长文本 | 文章内容、备注 |
| `DECIMAL(10,2)` | **精确小数** | ⭐ **金额必须用它**（10 位数字、2 位小数） |
| `FLOAT` / `DOUBLE` | 近似小数 | ❌ 不要用于金额（有精度误差） |
| `DATE` | 日期 | `'2026-10-20'` |
| `DATETIME` | 日期时间 | 范围大、不受时区影响 |
| `TIMESTAMP` | 时间戳 | 4 字节、受时区影响、范围到 2038 年 |
| `JSON` | JSON 文档 | 结构不固定的扩展字段（MySQL 5.7+） |

**三条最常考的选择题**：
1. **金额用 `DECIMAL` 不用 `FLOAT`**（浮点会算出 0.30000000000000004）。
2. **主键用 `BIGINT` 不用 `INT`**（业务量大了 INT 会溢出）。
3. **字符集用 `utf8mb4` 不用 `utf8`**（MySQL 的 `utf8` 只有 3 字节，存不了 emoji）。

## 5. 约束：让数据库自己保证数据正确

| 约束 | 作用 | 例 |
|---|---|---|
| `PRIMARY KEY` | 唯一 + 非空，一表一个 | `id INT PRIMARY KEY` |
| `UNIQUE` | 唯一（可多个，可为 NULL） | `email VARCHAR(100) UNIQUE` |
| `NOT NULL` | 不许空 | `name VARCHAR(50) NOT NULL` |
| `DEFAULT` | 默认值 | `score INT DEFAULT 0` |
| `AUTO_INCREMENT` | 自增（MySQL 专用） | `id BIGINT PRIMARY KEY AUTO_INCREMENT` |
| `FOREIGN KEY` | 引用完整性 | `FOREIGN KEY (dept_id) REFERENCES departments(id)` |
| `CHECK` | 条件检查（MySQL 8.0.16+ 才真正生效） | `CHECK (score >= 0)` |

> **主键 vs 唯一索引**（面试题）：主键不能 NULL、一表只有一个、InnoDB 里是聚簇索引；唯一索引可以多个、允许 NULL（多行 NULL 不算重复）、是二级索引。

## 6. 三范式与反范式

| 范式 | 一句话 | 反例 |
|---|---|---|
| **1NF** | 每列**不可再分** | 一个 `phone` 列存 "138, 139" 两个号码 ❌ |
| **2NF** | 在 1NF 上，非主键列**完全依赖**主键（不能只依赖复合主键的一部分） | 订单明细表（订单id, 商品id, 商品名, 数量）：商品名只依赖商品id ❌ |
| **3NF** | 在 2NF 上，非主键列**不能依赖其他非主键列**（不能传递依赖） | 员工表里存 `dept_id` 又存 `dept_name`：dept_name 依赖 dept_id ❌ |

**但真实项目会"反范式"**：故意冗余一些字段，换查询性能。

```text
订单表里冗余一个 user_name（规范上该通过 user_id 去用户表查）
好处：查订单列表不用 JOIN 用户表，快
代价：用户改名时要同步更新历史订单（一般接受"订单快照"语义，反而合理）
```

> 结论：**先按 3NF 设计，再为性能局部反范式，并说清代价。**

## 7. 表设计流程（10-26 周会实战，先有个框架）

```text
① 需求 → 列出所有"实体"和"它们之间的关系"
   例：用户、商品、订单；用户 1—N 订单，订单 N—N 商品
② 画 ER 图（实体 = 矩形，关系 = 菱形，属性 = 椭圆）
③ 转成表：
   实体 → 一张表
   N—N 关系 → 一张中间表（订单明细：order_id + product_id + 数量 + 单价）
   1—N 关系 → "多"的那张表加外键
④ 定字段类型、约束、默认值
⑤ 加索引（按查询需求，不是越多越好）
⑥ 写建表 SQL
```

**一个最小例子（订单）**：

```sql
CREATE TABLE orders (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id     BIGINT NOT NULL,
    total       DECIMAL(10, 2) NOT NULL DEFAULT 0,
    status      TINYINT NOT NULL DEFAULT 0,   -- 0待付 1已付 2已发 3完成
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE order_items (
    id         BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id   BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    price      DECIMAL(10, 2) NOT NULL,       -- 下单时的价格快照
    quantity   INT NOT NULL DEFAULT 1
);
```

## 8. 索引入门（今天只需"知道"，10-26 周深入）

**一句话**：索引 = 书的目录。没有索引，查一条数据要**全表扫描**（逐行看）。

**为什么是 B+ 树**：数据量大了，树的高度低（几百万行也就 3~4 层），且叶子节点相连、适合范围查询。

| 概念 | 一句话 |
|---|---|
| **聚簇索引** | InnoDB 的主键索引，叶子节点**直接存整行数据** |
| **二级索引** | 其他索引，叶子节点存**主键值** → 查其他列要**回表**（再按主键查一次） |
| **覆盖索引** | 查询的列都在索引里 → 不用回表（`EXPLAIN` 里显示 `Using index`） |
| **最左前缀** | 联合索引 `(a, b, c)`，能被 `a`、`a,b`、`a,b,c` 使用，**不能**被 `b`、`b,c` 单独使用 |

**什么时候建索引**：WHERE 条件列、JOIN 关联列、ORDER BY 列。
**什么时候别建**：写多读少的表、区分度极低的列（性别）、数据量很小的表。
**索引会拖慢写入**（每次 INSERT 都要维护索引）。

## 9. 事务与 ACID（面试最高频）

**事务 = 一组要么全成功、要么全不算数的操作。**

**ACID 四个特性**：

| 特性 | 含义 | MySQL 靠什么实现 |
|---|---|---|
| **A 原子性** | 要么全做，要么全不做 | undo log（回滚日志） |
| **C 一致性** | 从一种正确状态到另一种正确状态 | 由应用 + 约束共同保证 |
| **I 隔离性** | 并发事务互不干扰 | MVCC + 锁 |
| **D 持久性** | 提交后断电也不丢 | redo log（重做日志） |

**四种隔离级别**（MySQL 默认 **REPEATABLE READ**）：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---|:---:|:---:|:---:|---|
| READ UNCOMMITTED（读未提交） | ✅会 | ✅会 | ✅会 | 最不安全，几乎不用 |
| READ COMMITTED（读已提交） | ❌ | ✅会 | ✅会 | Oracle/PG 默认 |
| **REPEATABLE READ（可重复读）** | ❌ | ❌ | InnoDB 基本避免 | **MySQL 默认** |
| SERIALIZABLE（串行化） | ❌ | ❌ | ❌ | 最安全、最慢 |

**三个"读"的问题**：
- **脏读**：读到了别人**还没提交**的数据（对方一回滚，你就读错了）
- **不可重复读**：同一个事务里，两次读**同一行**，结果不一样（别人改了并提交了）
- **幻读**：同一个事务里，两次查**同一范围**，行数变了（别人插入并提交了）

```sql
-- 看 MySQL 当前隔离级别（8.0 用这个查）
SELECT @@transaction_isolation;
```

## 10. 锁（概念级，10-26 周展开）

| 锁 | 一句话 |
|---|---|
| **行锁** | InnoDB 按行加锁（并发好） |
| **表锁** | 锁整张表（MyISAM 只有表锁） |
| **共享锁 S** | 读锁，多个事务可同时拿 |
| **排他锁 X** | 写锁，独占 |
| **死锁** | 两个事务互相等对方的锁 → MySQL 会检测并**让其中一个回滚** |

> 实践：**事务里操作顺序保持一致**（都按 id 从小到大更新），能大幅降低死锁概率。

## 11. 存储引擎：InnoDB vs MyISAM

| | **InnoDB**（默认，8.0 唯一默认） | MyISAM（老引擎） |
|---|---|---|
| 事务 | ✅ 支持 | ❌ 不支持 |
| 锁 | 行锁 | 表锁 |
| 外键 | ✅ 支持 | ❌ 不支持 |
| 崩溃恢复 | ✅ redo log | ❌ 容易损坏 |
| 适用 | **几乎所有场景** | 只读/历史归档 |

> 建表时不用写 `ENGINE=InnoDB`（默认就是），但面试要能说出区别。

## 12. 视图 / 存储过程 / 触发器（知道"什么时候别用"）

| 对象 | 是什么 | 实践建议 |
|---|---|---|
| **视图 View** | 保存一条 SQL 的"虚拟表" | 简化复杂查询、权限隔离；但别层层嵌套（性能差） |
| **存储过程 Procedure** | 把一段 SQL 逻辑存在数据库里 | 现代后端**少用**：难版本控制、难调试、迁移困难 |
| **触发器 Trigger** | 表变动时自动执行 | **尽量别用**：副作用隐藏，排查困难 |

> 这一节的目标是**面试能答、被问到时能说清为什么不用**。

## 13. 权限与备份（知道命令即可）

```sql
-- DCL
CREATE USER 'app'@'%' IDENTIFIED BY 'strong_password';
GRANT SELECT, INSERT, UPDATE, DELETE ON practice.* TO 'app'@'%';
REVOKE DELETE ON practice.* FROM 'app'@'%';
FLUSH PRIVILEGES;
```

```powershell
# 备份 / 恢复
mysqldump -u root -p practice > backup.sql
mysql -u root -p practice < backup.sql
```

> 原则：**应用账号最小权限**（不要给生产库 root）。

## 14. 性能与安全（10-26 周深入，先有意识）

1. **别写 `SELECT *`**（多传无用列、破坏覆盖索引）。
2. **大表查询必须分页**（`LIMIT`），深分页要优化（`WHERE id > 上一页最大id LIMIT 10`）。
3. **EXPLAIN 看执行计划**：`type` 出现 `ALL` = 全表扫描，要警惕。
4. **SQL 注入**：绝对不要拼字符串：

```python
# ❌ 危险：name = "' OR '1'='1"
cursor.execute(f"SELECT * FROM users WHERE name = '{name}'")

# ✅ 参数化：驱动会处理转义
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
```
