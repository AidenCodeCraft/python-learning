## 一、先看问题：Day1 的代码哪里会"长胖"

假设再加 5 个列表接口，每个都要写：

```python
@app.get("/orders")
def list_orders(skip: int = 0, limit: int = 10):     # ① 分页参数每次重复
    settings = load_settings()                        # ② 配置每次重复
    db = open_db()                                    # ③ 打开资源
    try:
        ...
    finally:
        db.close()                                    # ④ 记得关（最容易忘）
```

**四个问题**：重复、容易漏、无法统一改、测试时不好替换。

**FastAPI 的答案 = 依赖注入（Depends）**：把这四件事写成"依赖函数"，接口只声明"我需要它"。

## 二、Depends 是什么

**一句话**：`Depends(f)` 告诉 FastAPI —— "**在执行这个接口函数之前，先调用 f()，把返回值塞进这个参数**"。

```python
def get_settings() -> dict[str, str]:
    return {"app_name": "商品 API", "version": "2.0.0"}

@app.get("/info")
def get_info(settings: dict[str, str] = Depends(get_settings)):
    #                       └────────┬────────┘
    #        框架先调用 get_settings()，把返回值赋值给 settings
    return settings
```

**执行顺序**：
```text
请求进来 → FastAPI 发现参数是 Depends(get_settings)
        → 调用 get_settings() 拿到 {"app_name":...}
        → 调用你的接口函数 get_info(settings={...})  ← 你的函数只写业务
        → 返回 JSON
```

> 和装饰器的区别：**装饰器包"整个函数"，依赖准备"参数"**。

### 为什么要这样写（三个好处）

| 好处 | 说明 |
|---|---|
| **去重** | 分页参数、配置、当前用户、数据库会话写一次到处用 |
| **可替换** | 测试时可以用 `app.dependency_overrides` 换成假数据（Day4 测试会用到） |
| **可组合** | 依赖里还能有依赖（依赖链） |

## 三、三种依赖写法（今天的 3 道题）

### 1. 类作为依赖（第 1 题 · 分页）

```python
from fastapi import Query

class Pagination:
    def __init__(
        self,
        skip: int = Query(default=0, ge=0),
        limit: int = Query(default=10, ge=1, le=100),
    ) -> None:
        self.skip = skip
        self.limit = limit

@app.get("/items")
def list_items(page: Pagination = Depends()):
    # FastAPI 会自己构造 Pagination(skip=..., limit=...)
    return ordered[page.skip: page.skip + page.limit]
```

要点：
- `Depends()` 什么都不传 = 让 FastAPI **按类型注解 `Pagination` 自己构造**
- 类里的 `Query(...)` 才能带**校验**（`limit=0` → 422）
- 为什么用类不用函数？**几个参数打包成一个对象**，接口签名干净

### 2. 普通函数依赖（第 2 题 · 配置）

```python
def get_settings() -> dict[str, str]:
    return {"app_name": APP_NAME, "version": APP_VERSION}

@app.get("/info")
def get_info(settings: dict[str, str] = Depends(get_settings)) -> dict[str, str]:
    return settings
```

真实项目里这里读环境变量（`pydantic-settings`）、Redis 地址、数据库密码。

### 3. `yield` 依赖（第 3 题 · 数据库会话）

```python
def get_db():
    STATE["db_opened"] += 1        # yield 之前 = 进入（相当于打开连接）
    try:
        yield "session"            # 把"会话"交给接口函数
    finally:
        STATE["db_closed"] += 1    # yield 之后 = 退出（响应发完之后一定执行）
```

```python
@app.get("/db-check")
def db_check(db: str = Depends(get_db)):     # db 就是 yield 出来的值
    return {"db": db, "opened": STATE["db_opened"]}
```

**关键理解**：
- `yield` 之前 = 请求前准备
- `yield` 之后（`finally`）= **响应发出后清理**，就算接口抛异常也会执行
- 这就是 Day1 那个"`try/finally` 关连接"的**框架化写法**
- 真实项目：`get_db()` yield 一个 SQLAlchemy `Session`，请求结束自动 close

## 四、中间件（Middleware）：每个请求都过的"关卡"

```python
import time
from fastapi import Request

@app.middleware("http")
async def add_process_time(request: Request, call_next):
    start = time.perf_counter()          # ① 请求进来的动作
    response = await call_next(request)  # ② 交给后面的处理（路由/依赖/接口）
    elapsed = (time.perf_counter() - start) * 1000
    response.headers["X-Process-Time"] = f"{elapsed:.2f}"   # ③ 响应出去前加工
    return response
```

**图形理解**：

```text
请求 → [中间件1] → [中间件2] → 依赖 → 接口函数
                                  ↓
响应 ← [中间件1] ← [中间件2] ←  ←  ←
```

### 中间件 vs 依赖（最容易混）

| | 依赖（Depends） | 中间件（middleware） |
|---|---|---|
| 作用对象 | **某个接口的参数** | **所有请求** |
| 能不能改响应 | 不能（只提供值） | 能（改 header/状态码/body） |
| 典型用途 | 取分页、开数据库会话、拿当前用户 | 日志、耗时、请求 ID、CORS、限流 |

## 五、CORS（第 5 题）：为什么前端调不到你的接口

**CORS** = 浏览器跨域限制：网页在 `localhost:3000`，接口在 `localhost:8000`，浏览器默认**不让**网页读响应。

服务器要明确告诉浏览器"我允许谁"：

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],   # 允许的源（* 表示所有）
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

**效果**：请求带 `Origin: http://localhost:3000` → 响应多一个头
`access-control-allow-origin: http://localhost:3000`。别的源就没有这个头。

> 生产别写 `allow_origins=["*"]` 还带 credentials（浏览器会拒绝）。

## 六、全局异常处理（第 6/7 题）：统一错误格式

Day1 里每个接口都 `raise HTTPException(404, "Item not found")`，前端拿到的格式是 `{"detail": "..."}`。
公司规范一般要求统一成 `{"code": 40400, "msg": "...", "data": null}` —— 用**全局异常处理器**做：

```python
class ItemNotFoundError(Exception):
    """业务异常：商品不存在。"""

@app.exception_handler(ItemNotFoundError)
async def item_not_found_handler(request: Request, exc: ItemNotFoundError):
    return JSONResponse(
        status_code=404,
        content={"code": 40400, "msg": "Item not found", "data": None},
    )
```

```python
@app.get("/items/{item_id}")
def get_item(item_id: int):
    if item_id not in ITEMS:
        raise ItemNotFoundError("Item not found")   # 不再是 HTTPException
```

**这样做的意义**：
- 业务代码只表达"什么错了"，不关心 HTTP 细节
- 格式统一 → 前端不用每个接口适配
- **一处修改，全局生效**（想加日志/上报就改 handler）

> 也可以给 `HTTPException` 注册 handler 做全局改造；公司脚手架通常就是这样统一响应的 —— 周五培训可以问老师。

## 七、lifespan（第 8 题）：应用启动/关闭时干什么

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动时执行：建数据库连接池、连 Redis、加载配置
    STATE["started"] = True
    yield
    # 关闭时执行：关连接池、刷缓存、打日志
    STATE["started"] = False

app = FastAPI(lifespan=lifespan)
```

**为什么需要**：
- 数据库连接池、Redis 客户端**不该每个请求都新建**（太慢），要在启动时建一次
- 关闭时优雅释放，避免连接泄漏

**注意**：`@app.on_event("startup")` 是旧写法（已弃用），**用 lifespan**。

## 九、常见报错

| 现象 | 原因 | 解决 |
|---|---|---|
| `TypeError: Object of type Pagination is not JSON serializable` | 直接把依赖对象 return 了 | 只 return 它的属性 |
| 接口参数没有默认值却报 422 | 依赖没写 `Depends` | `page: Pagination = Depends()` |
| `Depends()` 里类没构造出来 | 类 `__init__` 参数没写 `Query(...)` | 用 `Query` 声明 + 校验 |
| 中间件里取不到响应头 | 忘了 `await call_next(request)` | 用返回值 |
| `X-Process-Time` 不出现 | 中间件注册在 `app` 创建之前 / 拼错 header 名 | 检查顺序 |
| lifespan 没执行 | `TestClient(app)` 没用 `with` | `with TestClient(app) as c:` |
| 自定义异常没被处理 | `@app.exception_handler` 漏了 / 异常类型不匹配 | 检查注册 |
