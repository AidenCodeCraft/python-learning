# 05 · 为什么"能看懂、能填空，却无法从零做题"（2026-10-19）

> 触发：D5 的 `todo_cli` 项目骨架（3 个文件、11 个 TODO、要自己串起"命令行 → 数据类 → JSON 文件"），
> 你的原话："**完全无从下手，我能看懂怎么填，但是无法把之前的知识完全整合起来。**"
>
> 先给结论：**这不是能力问题，是练习类型缺失。** 下面解释机制和解法。

---

## 一、你的现象有一个准确的名字："能填空，不能构建"

| 任务类型 | 你要做的决策 | 你练过多少次 |
|---|---|---|
| 填空（骨架已给） | "这一步写什么" —— 上下文帮你做完了 80% 的决策 | **40+ 次**（D1–D4 的 50 多题里绝大多数） |
| 从零构建**多文件程序** | 数据结构 / 模块划分 / 调用顺序 / 错误处理 / 持久化 | **0 次** |

**你从来没练过"构建"，所以第一次构建时无从下手 —— 这是预期结果，不是失败。**

证据就在你自己的数据里：
- “20 题有骨架 + 有 `check()`” → 几乎全对；
- “`todo_cli` 没有骨架（只有函数签名）” → 无从下手。

---

## 二、四层原因（由浅到深）

### 原因 1：填空练的是"局部推理"，构建要的是"全局规划"

填空时，函数签名、docstring、上下文的变量名已经告诉了你：这段代码在干什么、输入是什么、输出是什么。
**你只需要回答"这一行写什么"**。

而从零构建时，所有问题都是开放的：

```text
数据用什么结构？ → 一个 Todo 类 + 一个 TodoStore
分成几个文件？   → todo.py（逻辑）/ cli.py（入口）/ test_todo.py
谁调用谁？       → cli → store → 文件
数据怎么流动？   → argv → 解析 → store.add → todos 追加 → json.dump → 返回
出错怎么办？     → 文件不存在 → 空列表；id 不存在 → 返回 False
```

**这些决策从来没被训练过，所以一见到它大脑就"空转"。**

### 原因 2：知识点是"孤岛"，缺"从需求到知识的路由"

你脑子里有这些点：`dict.get`、`sorted(key=)`、`json.load`、`for`、`class`、`try/except`……
但做题需要的是**路由**：

```text
"要做个存盘的待办清单"
    → 需要"一条数据" → 类
    → 需要"多条数据 + 操作" → 集合 + 方法
    → 需要"存盘" → json.dump / json.load + 路径
    → 需要"用户输入" → sys.argv / argparse
    → 需要"能验证" → pytest + 断言
```

**你的知识是散的，做题时检索不到。** 检索靠的是"关联"，关联只能靠"完整做过一次"建立。

### 原因 3："看懂"是跟随，"写出"是生成

- **看懂**：跟着作者的思路走（被动、低成本）—— 大脑会产生"我会了"的错觉。
- **写出**：自己做每一个决策（主动、高成本）。

两者之间隔着一道必须跨过的桥：**抄写 → 复述 → 改造**。你直接跳到了"造"，当然摔。

### 原因 4：你没有"设计"这一步，直接伸手写代码

看到 `todo_cli` 骨架，你的第一反应是"TODO 1 该写什么"。
正确的顺序是：

```text
① 先想清楚数据长什么样（举一个 JSON 例子）
② 再分模块、写每个模块一句话职责
③ 再写 5 步伪代码（中文）
④ 最后才动代码
```

**卡住的人 90% 都是"直接开始写代码"。** 写代码是最后一步，不是第一步。

---

## 三、解法：四段式"构建训练" + "三段设计法"

### 构建训练（读 → 抄 → 改 → 造）

| 段 | 做什么 | 目的 | 时间 |
|---|---|---|---|
| ① **读** | 读一份**完整可跑的参考实现**（100 行左右），逐行写注释说明"这行在干嘛、数据从哪来" | 建立"一个完整程序长什么样"的整体感 | 1h |
| ② **抄** | 关掉参考（允许偷看，但每行自己敲），**手抄**一遍，跑通 | 建立结构肌肉记忆 | 1.5h |
| ③ **改** | 在抄的版本上**加一个功能**（如 `search 关键词` 或 `list --priority`） | 学会在既有结构上扩展 | 1h |
| ④ **造** | 换一个**同类型不同主题**的程序（记账 CLI / 书签 CLI），从零写 | 真正的整合训练 | 2~3h |

> 这套方法在真实工作中也成立：接手公司项目 = 读 → 抄 → 改 → 造。

### 三段设计法（任何题，先写这三段，再写代码）

```python
# ① 数据长什么样？（举个具体例子）
#    例如：[{"id": 1, "title": "写代码", "done": false, "priority": 2}]

# ② 分几个部分？各自职责一句话
#    todo.py   —— 数据 + 逻辑，不打印不碰 argv
#    cli.py    —— 解析参数、调 store、打印
#    test_todo —— 用 tmp_path 验证

# ③ 分几步做？（伪代码，先不写实现）
#    1. 写 Todo（to_dict / from_dict / __str__）
#    2. 写 Store.load：文件不存在 → 空列表
#    3. 写 Store.save：mkdir + json.dump
#    4. 写 add / done / delete
#    5. 写 cli.main 分发
#    6. 写 3 个测试
```

**写不出这三段 = 还没想清楚，别动代码。** 先问教练。

## 四、本周的特殊情况：用 SQL 来补"整合能力"

这周要考 SQL（周五），**SQL 恰好是最好的整合训练材料**，因为它没有骨架可填：

```text
需求："每个部门平均工资最高的那个人是谁？"
   → 拆：先算每部门平均工资（GROUP BY + AVG）
   → 再找出比本部门平均高的人（JOIN 子查询）
   → 最后取最高/排序
```

**每一道 SQL 题都是"从需求到实现"的完整链路**，正是你缺的那种训练。
所以本周不需要额外挤时间做构建训练 —— SQL 练习本身就补了这块，只是领域从 Python 换成了 SQL。

（`todo_cli` 的"读→抄→改→造"训练排到 10-26 那周，那周时间充裕。）

## 五、判断标准：什么算"整合能力过关了"

- [ ] 拿到一个需求，能先写出"数据 + 模块 + 5 步伪代码"，而不是直接写代码
- [ ] 能独立写出一个 100 行左右、跨 2~3 个文件的程序，跑通且能自测
- [ ] 能把一个熟悉的功能换个主题重写（不是复制粘贴）
- [ ] 遇到报错能读 traceback 定位到"哪个模块、哪个函数、哪一行"

**这个能力不是"再学一个知识点"能解决的，只能靠"完整做 2~3 个小项目"长出来。**
